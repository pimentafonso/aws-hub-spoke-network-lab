# 6. Site-to-site VPN with BGP, active/standby, and a route table per spoke

- Status: accepted
- Date: 2026-11-20

## Context

M3 joins a simulated on-premises network (172.16.0.0/16) to the Transit
Gateway over an AWS Site-to-Site VPN. The design asks for three things the
M2 network could not give as it was:

- **On-prem reaches the hub and spoke A, not spoke B,** in both directions.
  M2 had one route table, `rt-spokes`, for both spokes. Propagating the VPN
  into it gives both spokes the same route to 172.16.0.0/16, which is more
  specific than the 172.16.0.0/12 blackhole. Spoke B's packets would then reach
  on-prem, and only the missing return route would stop the connection. The
  test would pass, but on-prem would be receiving traffic it should never see.
- **Both tunnels in use, and a failover that can be measured.** An AWS VPN
  connection always has two tunnels, to two AWS endpoints.
- **A customer gateway I control,** on a Free Tier instance type.

## Decision

**One route table per spoke.** `rt-spokes` becomes `rt-spoke-a` and
`rt-spoke-b`, each with the default route to the hub and the private-range
blackholes. Only `rt-spoke-a` has the VPN's routes propagated, so spoke B's
packets for on-prem hit the blackhole at the Transit Gateway. `rt-vpn`
propagates the hub and spoke A, so on-prem never learns spoke B's range.
TGW route tables are free.

| Route table | Associated | Propagated |
|---|---|---|
| rt-hub | hub | spoke A, spoke B, VPN |
| rt-spoke-a | spoke A | hub, VPN |
| rt-spoke-b | spoke B | hub |
| rt-vpn | VPN | hub, spoke A |

**The router** is a t4g.micro running Ubuntu 24.04 with strongSwan and FRR.
Amazon Linux 2023 has neither in its repositories. Each tunnel is
route-based: an XFRM interface matched to its IPsec SAs by `if_id`, with
traffic selectors of 0.0.0.0/0, so routing decides what enters a tunnel and
BGP decides the routes. The router's Elastic IP is the customer gateway's
address. It also masquerades the on-prem test host's internet traffic, which
the host needs to reach SSM.

**Active/standby, not ECMP.** The Transit Gateway supports ECMP across VPN
tunnels. Linux can do it too, but with ECMP a cut tunnel loses only the flows
hashed onto it, and the measurement depends on that hashing. With
active/standby, every flow moves at once, so one cut gives one clear outage:

- on-prem to AWS: routes from tunnel 1 get local-pref 200, routes from tunnel 2 get 100;
- AWS to on-prem: on-prem prepends its AS three times on tunnel 2, and the
  Transit Gateway prefers the shorter AS path.

**Timers.** AWS's defaults: 30 s dead peer detection, BGP keepalive 10 s and
hold 30 s. FRR uses the same BGP timers. AWS VPN does not support BFD, so the
hold timer sets the floor for detecting a silent failure.

**Pre-shared keys** are generated by AWS. Terraform stores them as SecureString
parameters under `/nwlab/vpn/`, and the router reads them at boot. They never
pass through user data, which anyone with `ec2:DescribeInstanceAttribute` can
read, including the read-only CI role. The router's role, and the permissions
boundary, allow `ssm:GetParameter` on that path only, and `kms:Decrypt` only
through SSM.

**The failover test** (`scripts/failover.py`) cuts tunnel 1 on the router by
dropping all its traffic to and from that tunnel's AWS endpoint. Neither side
gets a goodbye, as with a failed link. It measures:

- the outage seen by a TCP connection every 0.2 s from on-prem to spoke A;
- the time to FRR's "Down" for the tunnel 1 neighbour;
- which interface carried traffic in each phase;
- the time to "Up" after the restore.

It does this three times.

## Consequences

- One more route table per spoke. A third spoke means another table and
  another blackhole set, which is acceptable at this size. With many spokes, a
  shared table plus security groups, or AWS Network Firewall, would scale
  better.
- Spoke B's deny is enforced by the Transit Gateway, so on-prem never sees the
  packet. The M4 flow logs can show that: no record of spoke B in on-prem's
  logs.
- The router is a single instance with no failover of its own. The test
  measures tunnel failover, not router failover.
- After a cut, strongSwan retries for ever (`keyingtries = 0`). The test then
  re-initiates the tunnel at once, so the failback time does not depend on
  where strongSwan's retry backoff happens to be.
- Its configuration lives in user data and is not persisted across a reboot.
  The router lasts one session.
